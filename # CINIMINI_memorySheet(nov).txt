# CINIMINI
## Technical Memory Sheet – Frontend & Backend
**Version:** November 2026  
**Purpose:** Preserve the current architecture, implementation details, debugging history, and pending work.

---

# 1. PROJECT OVERVIEW

CiniMini is a platform for young filmmakers to publish and discover short films, teasers, trailers, and other video content.

### Current Technology Stack

| Layer | Technology |
|---|---|
| Frontend | Flutter |
| Navigation | GoRouter |
| Backend | Node.js + Express |
| Video platform | PeerTube |
| Video streaming | HLS |
| Main Flutter player | MediaKit |
| Alternative player experiment | video_player |
| Video thumbnails | CachedNetworkImage |
| HTTP communication | http package |
| Future storage integration | Google Drive |

### Important Architectural Decision

**PeerTube is our selected video processing and streaming engine.**

Google Drive is intended for future persistent storage integration. The older Google Drive-based HLS implementation is an experiment and is not the selected user-facing playback architecture.

Do not confuse these two systems.

# 4. VIDEO DATA ARCHITECTURE

## 4.1 Video Model

File:

`lib/models/video_model.dart`

Current fields:

- id
- uuid
- title
- thumbnail
- channel

The model maps PeerTube API response fields:

| Flutter field | PeerTube response field |
|---|---|
| id | id |
| uuid | uuid |
| title | name |
| thumbnail | thumbnailPath |
| channel | channel.displayName |

The thumbnail helper:
- Returns an absolute URL unchanged.
- Otherwise combines the thumbnail path with the configured PeerTube base URL.

There is also an `hlsUrl` getter that constructs:

`/static/streaming-playlists/hls/{uuid}/master.m3u8`

However, this is not the current main playback method. The main player fetches the actual playlist URL dynamically through the video-details API.

Do not assume this getter is correct or used without checking its references.

## 4.2 Video Listing Service

File:

`lib/services/video_services.dart`

Class: `VideoService`

Responsibilities:
- Sends GET request to PeerTube's videos endpoint.
- Expects a JSON response containing a `data` list.
- Converts each item into a VideoModel.
- Throws an exception for unsuccessful responses.

## 4.3 Video Repository

File:

`lib/repositories/video_details_repositories.dart`

The supplied filename was plural, although some imports refer to a singular filename. Verify the actual path if necessary.

`VideoRepository`:
- Supports dependency injection of VideoService.
- Provides `getVideos()`.

The architecture separates data access from UI components.

# 5. VIDEO DETAILS AND PLAYBACK URL

## 5.1 Video Details Service

File:

`lib/services/video_details_service.dart`

Class:

`VideoDetailsService`

Method:

`fetchPlayableVideo(String uuid)`

Current workflow:

1. Receives a PeerTube video UUID.
2. Requests:

   `/api/v1/videos/{uuid}`

3. Checks whether `streamingPlaylists` exists.
4. Checks whether the playlist list is empty.
5. Extracts the first playlist's `playlistUrl`.
6. Normalizes the URL using ApiConfig.
7. Returns the playable HLS URL.

Important: The playlist URL is obtained dynamically from PeerTube.

It is not supposed to be hardcoded in the VideoModel.

## 5.2 Video Details Repository

`VideoDetailsRepository`

Responsibilities:
- Creates VideoDetailsService.
- Exposes `getPlayableVideo(uuid)`.
- Keeps the player screen separate from direct HTTP implementation.

| Platform | Default |
|---|---|

Default PeerTube URL:

| Platform | Default |
|---|---|
| Web | localhost:9000 |
| Android emulator | 10.0.2.2:9000 |

When LAN_HOST is supplied, Android uses that host for both backend and PeerTube.

Previously used command:

```bash
flutter run --dart-define=LAN_HOST=192.168.197.175
```

That IP is historical and must not be assumed to be the current LAN IP.

### URL normalization

`normalizePeerTubeUrl()` replaces localhost and 127.0.0.1 hosts with the configured PeerTube host.

It does not currently handle every possible hostname.

File:

Important:


# 12. PEERTUBE BACKEND SERVICE

## 12.1 PeerTube Service

File:

`src/services/peertubeService.js`

Responsibilities:

- Obtains PeerTube OAuth client details.
- Requests an access token.
- Uploads videos to PeerTube.
- Returns video ID, UUID, short UUID, watch URL, and raw response.

Upload API:

```text
POST /api/v1/videos/upload
```

Authentication uses a Bearer token.

The upload service:
- Validates file path and title.
- Reads the uploaded file.
- Creates a Blob and FormData.
- Sends the upload request to PeerTube.
- Uses `waitTranscoding: false` in the upload route.

Current implementation reads the entire file into memory before upload. This is a future scalability consideration, not a confirmed playback issue.

## 12.2 PeerTube Configuration

File:

`src/config/peertubeConfig.js`

Centralizes:

- PEERTUBE_URL
- PEERTUBE_API_URL
- Username
- Password
- Channel ID

Some other services read environment variables independently instead of importing this configuration.

This is an architectural observation, not an immediate reason to refactor.

## 12.3 PeerTube Status Service

File:

`src/services/peertubeStatusService.js`

Responsibilities:

- Obtains an OAuth access token.
- Requests video details from PeerTube.
- Checks processing state.
- Checks HLS availability.
- Extracts playlist and file metadata.

It examines fields such as:
- State ID and label.
- Streaming playlists.
- Playlist type.
- Playlist URL.
- File resolution.
- Width and height.
- Audio/video availability.
- File size and FPS.
- File URLs.

Current completion logic checks:

```text
stateId === 1
HLS available
HLS files exist
```

This service supports the upload/transcoding/storage-transfer workflow.

It is not the service used by the main Flutter playback screen.

# 13. BACKGROUND HLS PROCESSING

File:

`src/services/hlsProcessingService.js`

Current workflow:

```text
Video uploaded to PeerTube
        |
        v
Start background processing job
        |
        v
Poll PeerTube status every 15 seconds
        |
        v
Check processing completion
        |
        v
Check HLS availability
        |
        v
Transfer HLS assets to Google Drive
        |
        v
Mark job COMPLETED or FAILED
```

Configuration:
- Polling interval: 15 seconds.
- Maximum attempts: 120.
- Approximate maximum polling duration: 30 minutes.

The service uses an in-memory `processingJobs` Map.

Consequently, job status is not persistent across backend restarts.

**Architectural distinction:** This is a PeerTube-to-Drive background transfer workflow. It is not the current Flutter playback pipeline.

# 14. BACKEND PEERTUBE ROUTES

File:

`src/routes/peertubeRoutes.js`

### Upload endpoint

```text
POST /api/peertube/upload
```

Workflow:
1. Receives video using multer.
2. Extracts title, name, description, category, and privacy fields.
3. Calls PeerTube upload service.
4. Starts background HLS processing.
5. Returns PeerTube upload information.
6. Deletes the temporary uploaded file.

### Processing status endpoint

```text
GET /api/peertube/processing-status/:videoUUID
```

Returns the in-memory processing job status.

These routes currently handle uploading and background processing, not main video playback.

# 15. OLD GOOGLE DRIVE HLS IMPLEMENTATION

This section must remain separate from the selected PeerTube playback architecture.

## 15.1 HLS Routes

File:

`src/routes/hlsRoutes.js`

Routes mounted under `/api`:

```text
GET /api/videos/:videoUUID/hls/master.m3u8

GET /api/videos/:videoUUID/hls/media.m3u8

GET /api/videos/:videoUUID/hls/video.mp4
```

The routes call `hlsStreamingService`.

The MP4 endpoint:
- Retrieves a Google Drive file ID.
- Reads the Range header.
- Requests file content from Drive.
- Forwards streaming headers.
- Streams the response to the client.

## 15.2 HLS Streaming Service

File:

`src/services/hlsStreamingService.js`

Current implementation:
- Uses `driveService`.
- Maintains a hardcoded video-assets Map.
- Retrieves playlist content from Drive.
- Reads playlist content into memory.
- Validates the `#EXTM3U` header.
- Rewrites playlist references.
- Provides master and media playlists.

One hardcoded UUID identified:

`e9713faa-0591-460e-a16f-d51063de1dd1`

This implementation represents an older Google Drive HLS experiment.

It must not be treated as the current PeerTube playback engine.

# 16. CURRENT PLAYBACK ISSUE

## 16.1 Device and Environment

Latest confirmed primary test device:

**Redmi M2006C3LI**

Previously used:
- Infinix X669C
- Android 12 / API 31

Current Redmi Android version has not been reconfirmed.

Laptop:
- Windows 11
- VS Code

Flutter build and installation have succeeded.

## 16.2 Observed Symptoms

| Video | Duration | Observed behaviour |
|---|---:|---|
| Waste shortfilm | ~1:59 | Starts around 26 seconds |
| Inevitable | ~13 seconds | Starts around 6 seconds, later around 9 seconds |
| Karma teaser | ~19 seconds | Plays briefly, then ends after around 1 second |

Chrome on Android can play the PeerTube master HLS URL correctly.

MediaKit has shown abnormal seeking, jumping, and early completion behaviour on the Redmi.

## 16.3 Previous MediaKit Log Findings

Log date: 15 November 2026.

Observed:
- HLS master and child playlists fetched.
- Media fragments fetched.
- MediaKit recognized a duration of approximately 18.917 seconds.
- H.264 video, 848 × 480, 24 FPS.
- AAC stereo audio, 44.1 kHz.
- Initial software decoding.
- Android surface became available later.
- Video output changed from a null output to Android output.
- Decoder and output were reinitialized.
- Playback completed at the reported duration.

No obvious HTTP or Range failure was established.

Late surface creation and output reconfiguration are possible investigation leads, not proven root causes.

## 16.4 Latest Android Log Findings

Log date: 23 November 2026.

Observed:
- APK installation and application launch succeeded.
- Impeller OpenGLES was active.
- Significant skipped frames and main-thread delays occurred during launch.
- PeerTube URLs were normalized to the LAN IP.
- Android MediaCodec/ACodec initialized.
- Video output surfaces were created.
- AudioTrack started.
- VideoOutput disposal and recreation occurred across video screens.
- Some Android rendering and audio warnings appeared.

The log does not establish a definitive cause of the abnormal playback.

Do not assume that every warning is responsible.

# 17. CURRENT TECHNICAL HYPOTHESES

1. MediaKit/MPV playback behaviour on the Redmi device.

# 18. DEVELOPMENT RULES FOR THE NEXT PHASE

These decisions must be preserved.

1. Do not replace the current MediaKit player without a controlled comparison.
2. Do not delete the existing player implementation.
3. Do not confuse the Google Drive HLS experiment with PeerTube playback.
4. Do not hardcode a new HLS URL when PeerTube already provides the playlist URL dynamically.
5. Do not redesign the frontend or backend unnecessarily.
6. Do not change multiple variables in one playback experiment.
7. Use the same video and same PeerTube playlist when comparing player packages.
8. Keep the current architecture intact unless actual evidence requires a change.
9. Distinguish confirmed facts from hypotheses.
10. Review existing files before proposing code modifications.
